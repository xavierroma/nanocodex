# nanocodex-memory

MIT-licensed managed memory for an agent: markdown records the agent reads during a
task, a nightly reconciliation that is the only thing allowed to write them,
and the store that keeps them versioned. This crate owns the file contract,
the store, the sync into and out of the agent's VM, and the reconciliation
rules. It does not own scheduling, the VM or the model loop; the agent service
supplies those.

The design is Instinct's opinionated file model with OpenClaw's tiers and
provenance rules: memory is plain files, one record per thing with an ID, a
type and aliases, dated facts and links between records; the agent reads and
greps them; a background pass writes them; nothing reaches the curated tier
without passing through that pass.

## The files

One bundle per owner. A host can expose it through memory tools or optionally mirror it into a VM at `/home/user/memory`:

```text
profile.md              one-pager, generated by reconciliation, read every task
index.md                every record's id, type, aliases and one line, generated
preferences/<id>.md     what the person likes, wants, and how the agent should behave
people/<id>.md          people in the person's life and how they relate
places/<id>.md          home, work, places they go, addresses
accounts/<id>.md        services and websites the person uses; never a credential
tasks/<id>.md           things asked for that are not finished, or that recur
journal/YYYY-MM-DD.md   the agent's own dated notes while it works, append only
log/YYYY-MM-DD.md       what reconciliation changed that day and why
```

A record:

```markdown
---
id: dining
type: preference
aliases: [food, lunch, restaurants, takeout, delivery, dining]
updated: 2026-09-21
---
- **Pasta:** Loves pasta; said so on 2026-09-15.
- Orders dinner around 19:30 on weekdays (2026-09-18).
- Related: [[home]], [[partner-maria]]
```

Rules the reconciliation keeps and `lint` checks:

- The front matter has `id`, `type`, `aliases` and `updated`. The id is the
  file name and is lowercase letters, digits and hyphens. The type is the
  directory.
- Facts are dated bullets, one fact each. A correction replaces the fact and
  keeps the date of the correction; it does not append a contradiction beside
  the old fact.
- `[[id]]` links name other records that exist.
- Aliases are how a grep finds the record, so every name the person uses for
  the thing goes there.
- A record is short. Detail that does not change what the agent should do
  goes to the journal, not the record.

`profile.md` is the only file with a reserved shape: life context, how the
person wants the agent to act, how they want to be talked to, and open tasks.
It is at most 6,000 characters. `index.md` is generated deterministically from
the records and is what the agent reads to know what memory it has.

## API integration

The managed API uses persistent agent IDs as owners and stores bundles and versions
in its SQLite database on a Kubernetes PVC. It supplies memory read, search, and
journal tools without a VM. Its reconciliation worker checks pending completed
tasks every minute and edits a private draft through memory tools. Validation and
a revision check protect the complete stored bundle. See `services/api/README.md`
for routes, limits, deletion, and provider disclosure.

The VM workflow below is an optional integration provided by this crate. The crate
does not require a VM or a fixed schedule.

## Who writes what

| Tier | Files | Written by | Read |
| --- | --- | --- | --- |
| Curated | `profile.md`, `index.md`, `<type>/<id>.md` | Reconciliation only | Installed in the VM every task; `profile.md` and `index.md` also in the instructions |
| Episodic | `journal/YYYY-MM-DD.md` | The agent, during a task, append only, today's file only | Installed in the VM; never in the instructions |
| Audit | `log/YYYY-MM-DD.md` | Reconciliation | For people |

The agent's shell can write anywhere in `/home/user/memory`, since the VM is
its computer. The store only takes back today's journal. Every other change
the agent makes to memory during a task is discarded when the next task
installs the bundle again. That is how "the agent reads, reconciliation
writes" holds without a read-only filesystem.

## Provenance

Reconciliation is given the day's material with its origin, and the rules say
what each origin may become:

- **The person's own words**, the prompts of the day's tasks, may become any
  record.
- **What the agent reported back**, the final messages, may become records of
  what was done and what the agent learned about the person.
- **The journal**, written by the agent while working, may become records, but
  a journal line that quotes a web page, a file or a tool output is evidence,
  not a fact about the person, and stays out of the curated tier.
- Nothing from a failed or cancelled task is material.

There is no automatic forgetting. An explicit "this is not happening" removes
the fact; a stale fact stays until reconciliation, reading it against the day's
material, decides it is stale. History survives in the store's object versions
and in the log.

## Reconciliation

Once a day, for every owner who had a completed task since the last run, the
agent service runs one task on the owner's own VM on the reserved thread
`memory`, with no phone tools. Its prompt is this crate's, built from the day's
material and the current bundle. The model edits the files in
`/home/user/memory`; the service collects the result, this crate validates it,
regenerates `index.md`, writes the day's log, and stores the new bundle. A
result that fails validation is rejected whole and logged; the previous bundle
stays.

What the prompt asks for, in Instinct's words: move temporary details into
tasks, shorten durable records and link to fuller notes, turn examples into
broader traits, remove incidental detail, replace wrong facts with dated
corrections, and keep ids, types, aliases and links intact.

## The store

`MemoryStore` is one trait: load an owner's bundle, save a set of changes.
`LocalMemoryStore` is a directory, for tests and local runs. `GcsMemoryStore`
is one Cloud Storage bucket per deployment with one prefix per owner, using
object versioning as the history. A bucket per person was considered and
rejected: buckets are a scarce, rate-limited resource in a project, and only
the agent service ever reads them, so per-owner isolation is a prefix, and
per-owner access control is the service's.

## What this crate does not do

It does not schedule the nightly run, submit the task, or hold the VM: the
agent service does, through its store for the list of owners and its runner
for the VM. It does not search: the agent greps the files. It does not
decide provenance itself: the reconciliation prompt carries the rules and the
validator checks the shape, not the truth.
